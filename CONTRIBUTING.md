# Руководство по внесению изменений

Этот документ описывает порядок совместной работы над
стайлгайдом технической документации.

Изменения в правилах оформления, примерах и структуре
документации вносятся через отдельные ветки и Pull Request.

## Предложение новых правил

Перед добавлением нового правила необходимо:

1. Проверить, нет ли аналогичного правила в существующих разделах.
2. Определить, какую проблему решает новое правило.
3. Подготовить краткую и однозначную формулировку.
4. По возможности добавить пример правильного и неправильного оформления.
5. Обсудить изменение с другим участником проекта.

Если правило относится к уже существующей теме, его следует
добавить в соответствующий раздел. Для отдельной темы можно
создать новый Markdown-файл.

## Работа с ветками

Не рекомендуется вносить изменения непосредственно в `main`.

Для каждой задачи создавайте отдельную ветку от актуальной
версии `main`.

Пример:

```bash
git switch main
git pull origin main
git switch -c docs/update-markdown-rules
```

Название ветки должно кратко отражать содержание изменений.

## Оформление коммитов

Для сообщений коммитов используется соглашение
Conventional Commits.

Формат:

```text
<type>: <description>
```

Основные типы:

| Тип | Назначение |
| --- | --- |
| `docs` | Добавление и изменение документации |
| `fix` | Исправление ошибок |
| `chore` | Настройка инструментов и служебные изменения |
| `ci` | Изменение процессов CI/CD |

Примеры:

```text
docs: add accessibility guidelines
fix: correct broken documentation links
chore: configure Markdown linting
ci: add documentation checks
```

Сообщение должно быть кратким и отражать фактические изменения.

## Создание Pull Request

После внесения изменений:

1. Проверьте документацию локально.
2. Создайте коммит.
3. Отправьте ветку в GitHub.
4. Создайте Pull Request в ветку `main`.
5. Добавьте описание внесённых изменений.
6. Дождитесь автоматических проверок и ревью.

Пример команд:

```bash
git add .
git commit -m "docs: update documentation rules"
git push -u origin docs/update-markdown-rules
```

## Проверка изменений

Каждый Pull Request должен пройти проверку другим участником.

При ревью необходимо обратить внимание на:

- соответствие правилам стайлгайда;
- понятность формулировок;
- корректность примеров;
- единообразие терминологии;
- правильность Markdown-разметки;
- отсутствие ошибок сборки MkDocs.

Замечания рекомендуется оставлять к конкретным строкам файлов.

После исправления замечаний автор обновляет Pull Request
новым коммитом. Повторная проверка проводится до объединения
изменений с `main`.

## Локальная проверка документации

Для работы с проектом необходимы Python и Node.js.

Создайте виртуальное окружение:

```bash
python3 -m venv .venv
source .venv/bin/activate
```

Установите зависимости:

```bash
python -m pip install -r requirements.txt
```

Проверьте Markdown-файлы:

```bash
npx --yes markdownlint-cli2
```

Проверьте сборку документации:

```bash
python -m mkdocs build --strict
```

Для локального просмотра сайта выполните:

```bash
python -m mkdocs serve
```

После запуска MkDocs сайт обычно доступен по адресу
`http://127.0.0.1:8000/`.

## Добавление нового раздела

Чтобы добавить новый раздел стайлгайда:

1. Создайте Markdown-файл в каталоге `docs/`.
2. Добавьте заголовок первого уровня.
3. Опишите правила и приведите примеры.
4. Добавьте новый файл в раздел `nav` файла `mkdocs.yml`.
5. Проверьте отображение страницы локально.
6. Выполните Markdownlint и сборку MkDocs.
7. Создайте Pull Request для проверки изменений.

Имя нового файла должно состоять из латинских букв
в нижнем регистре. Слова разделяются дефисами.

## Автоматические проверки и публикация

Для каждого Pull Request GitHub Actions запускает:

- проверку Markdown с помощью Markdownlint;
- сборку документации с помощью MkDocs.

После объединения изменений с веткой `main` и успешного
завершения проверок сайт автоматически публикуется
на GitHub Pages.

Не объединяйте Pull Request, если обязательные проверки
завершились с ошибками.
